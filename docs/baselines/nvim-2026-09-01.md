# Baseline de Neovim — 2026-09-01

## Entorno

- Neovim: `0.12.5` (LuaJIT 2.1.1787165859)
- Configuración: `stow/nvim/.config/nvim/init.lua`
- Leader: espacio
- Plugins registrados por lazy.nvim: `59`
- Entradas del lockfile: `60`
- HOME real y configuración local no se modificaron durante la medición.

## Carga headless

Cinco ejecuciones consecutivas de:

```bash
nvim --headless -u stow/nvim/.config/nvim/init.lua '+qa'
```

Resultados observados: `0.382 s`, `0.529 s`, `0.351 s`, `0.332 s`, `0.361 s`.
La mediana aproximada es `0.361 s`; el máximo puntual fue `0.529 s`.

La configuración carga sin error headless, conserva `mapleader = " "` y
registra `:CodexExplain`.

## Carga eager observada

- `nvim-treesitter` y `nvim-treesitter-textobjects`: `lazy = false`.
- `nvim-ts-autotag` y context-commentstring: `lazy = false`.
- `vim-tmux-navigator`: `lazy = false` para conservar navegación desde el
  primer buffer.
- Varios plugins de UI/motion/which-key usan `VeryLazy`.

## Hallazgos iniciales

1. La configuración actual ya tiene lazy-loading amplio; no hay evidencia en
   este baseline para mover más plugins a eventos tardíos.
2. Hay declaraciones activas duplicadas para Comment.nvim y
   nvim-ts-context-commentstring entre `comment.lua`, `editing.lua` y
   `treesitter.lua`; deben consolidarse antes de comparar rendimiento.
3. La cobertura backend existe en `lua/lang/php.lua`, task runner, neotest,
   conform/nvim-lint y DAP/Xdebug.

## Reglas de comparación

- Comparar medianas de cinco ejecuciones, no el mejor caso.
- Verificar arranque headless y disponibilidad de mappings/comandos tras cada
  cambio.
- No actualizar todo `lazy-lock.json` como parte de una optimización.
- Mantener tmux, i3, `.bashrc_local` y la integración Bash fuera del diff.

## Seguimiento tras la auditoría

Tras consolidar el ownership de plugins y los contratos de workflows, se
repitieron cinco ejecuciones con el mismo comando: `0.347 s`, `0.396 s`,
`0.374 s`, `0.441 s`, `0.522 s`.

La mediana observada fue `0.396 s`. La diferencia frente al baseline (`0.361
s`) está dentro de la variabilidad de ejecuciones puntuales y no aporta una
optimización segura demostrable. Por ello esta fase no modifica la estrategia
de lazy-loading ni añade carga diferida.
